De la galerie aux piliers : anatomie du moteur PostKit

Comment 5 000 photos non triées deviennent une bibliothèque rangée par sujet, en silence et de manière reprenable. Cette doc explique la pipeline de classification de la galerie : ses briques, l'algorithme, et ce qui se réutilise tel-quel dans une future app.

01. Mission du moteur

L'utilisateur arrive avec une pellicule remplie au hasard sur plusieurs années. Le moteur a deux jobs : scanner toute la galerie sans bloquer l'UI ni vider la batterie, et classer chaque photo dans un ou plusieurs « piliers » (sujets de contenu définis par l'utilisateur) avec un score de confiance.

Contraintes qui ont guidé le design

  • Idempotence. Le scan complet peut être interrompu (kill, low-battery, perte d'accès photo) et doit reprendre exactement où il s'est arrêté, sans reclasser ce qui est déjà fait.
  • Gratuité par défaut. 99% du travail est on-device via Core ML / Vision. La cloud AI (Gemini) n'est appelée que sur les cas ambigus, opt-in, et derrière un signal minimum.
  • Backpressure naturelle. Pas de buffer mémoire qui grossit : la galerie alimente le pipeline à la vitesse où le ML peut digérer.
  • UI jamais bloquée. Le ModelContext principal sert à la lecture UI ; toutes les écritures lourdes se font sur un background context.
  • Snapshot first. Les @Model SwiftData ne traversent jamais les frontières d'actor — on convertit en structs Equatable/Sendable dès qu'on quitte le contexte du store.

03. Les six briques

Chaque brique est un @DependencyClient injectable (live / preview / test). Le contrat est l'interface ; l'implémentation se swap sans toucher au reducer.

PhotoLibraryClient

Dependencies/PhotoLibraryClient.swift
I/O · PhotoKit

Wrap minimal sur PhotoKit. Expose la galerie comme : un comptage, un Set<String> de tous les localIdentifier (pour dédupliquer le scan), un fetch des N plus récentes, le streaming complet via PhotoBatchSequence, et la résolution d'une image (thumb ou full).

La méthode image(identifier, size) bascule entre fastFormat / highQuality selon la taille demandée — on ne paie le coût d'une décompression haute-déf que pour la classification.

Pattern réutilisable : exposer PhotoKit via une interface @Sendable au lieu de propager PHAsset dans le code métier. PhotoAsset (le DTO) ne porte que localIdentifier · creationDate · location.

PhotoBatchSequence

Dependencies/PhotoBatchSequence.swift
Streaming · backpressure

Une AsyncSequence qui yield des batches de N PhotoAsset à la demande. Remplace un AsyncStream bufferisé — qui chargeait toute la galerie en RAM pendant que le ML rattrapait.

Chaque appel à next() énumère le batch suivant depuis PHFetchResult, fait un Task.yield() pour redonner du CPU aux tâches ML concurrentes, et propage CancellationError immédiatement.

Trois modes : .live(batchSize) pour la prod, .static(batches) pour les tests, .pending qui ne yield jamais (utile en preview).

Pattern réutilisable : dès qu'un producteur peut être plus rapide que le consommateur, préférer une AsyncSequence pull-based à un AsyncStream buffer. La backpressure est automatique.

ImageClassifierClient

Dependencies/ImageClassifierClient.swift
Brain · ML hybride

Le cœur. Trois méthodes : classify, detectCadrage, et classifyWithCadrage qui fait les deux en réutilisant la même passe Vision.

L'implémentation interne est divisée en trois enums privés : VisionClassifier (on-device), GeminiClassifier (cloud), et CadrageDetector (orientation/style).

Seuils : highConfidence = 0.70 (Vision suffit), minConfidence = 0.55 (gardé en résultat), geminiFloor = 0.30 (signal Vision minimum avant d'appeler le cloud).

Pattern réutilisable : ne jamais appeler le cloud par défaut. On-device first, fallback derrière un flag utilisateur (cloudAIEnabled) ET derrière un signal minimum de l'on-device. Économise quota API et préserve la vie privée.

PersistenceClient

Dependencies/PersistenceClient.swift
Storage · SwiftData

Wrap sur SwiftData. Sépare un mainContext (lecture UI) d'un backgroundContext (écritures lourdes). Aucune view ne touche au context directement — tout passe par cette interface.

API expose surtout des fetch... qui renvoient des Snapshots (PillarSnapshot, ClassifiedPhotoSnapshot, etc.) — des structs Equatable/Sendable qui peuvent traverser les frontières async sans risque.

Méthodes critiques pour le scan : fetchClassifiedAssetIDs() → Set<String> (idempotence), batchSavePhotos([Snapshot]) (un seul save par batch).

Pattern réutilisable : snapshot pattern obligatoire avec SwiftData. @Model n'est ni Sendable ni Equatable — ne jamais le stocker dans un State TCA ou le passer entre actors.

GalleryClient

Dependencies/GalleryClient.swift
Cache · actor

Couche de lecture cachée par-dessus PersistenceClient. Les vues (Dashboard, Explore, Post Assembly) lisent des dizaines de fois ; on évite des dizaines de hits DB en mettant un actor en cache.

Quatre caches : pillars, photos, templates, posts. Chacun avec son invalidate appelé par les reducers qui écrivent (e.g. acceptAllTapped → invalidatePhotos).

Pattern réutilisable : un actor entre la DB et les reducers — invalidation explicite côté écriture, jamais d'invalidation automatique. Le contrôle reste lisible.

Reducers d'orchestration

Features/Dashboard/DashboardFeature.swift · Features/Classification/ClassificationQueueFeature.swift
TCA · effects

Aucune brique ne s'orchestre toute seule. Le full scan vit dans DashboardFeature.runFullScan et le review queue (photos à valider manuellement) dans ClassificationQueueFeature.

Le run effect est marqué .cancellable(id: CancelID.fullScan). Quitter l'app, basculer l'utilisateur ou rappuyer "Scan" annule proprement la TaskGroup et tous les await en cours.

Pattern réutilisable : tout effect long doit avoir un .cancellable(id:). Et CancellationError doit toujours être re-throw — jamais catch {} qui l'avale silencieusement.

04. L'algorithme de classification

Le matching photo → pilier ne fait pas d'embeddings, ne fait pas de fine-tuning. C'est un token-matcher Vision : simple, déterministe, gratuit, et étonnamment robuste sur les catégories larges.

Étape 1 — Vision sort des identifiers

Le request VNClassifyImageRequest renvoie ~1 000 observations comme { identifier: "sports_car", confidence: 0.82 }, { identifier: "espresso", confidence: 0.71 }, etc. La plupart sont du bruit ; on filtre confidence > 0.01 pour garder ce qui est utilisable.

Étape 2 — Construction du vocabulaire de chaque pilier

Pour chaque pilier défini par l'utilisateur, on construit un Set<String> de termes :

  • Reference tags — les tags des photos d'exemple que l'utilisateur a uploadées au setup (signal le plus fort).
  • Mots de la description — l'utilisateur a écrit "cars, motorsport, garage builds". On tokenise, on garde les mots de plus de 3 caractères.
  • Fallback keywords — une table hardcodée pour les catégories génériques ("automotive" → car/vehicle/auto/truck/motor/road/wheel/race/drive…). Sert de filet quand l'utilisateur ne donne ni description ni tags.
  • Le nom du pilier — toujours inclus, splité sur l'espace.

Étape 3 — Matching tokenisé

L'identifier Vision "sports_car" est splité sur _ → {"sports", "car"}. Pour chaque pilier on regarde si un token Vision matche un terme du vocabulaire (égalité OU préfixe si le terme fait ≥ 4 caractères).

Quand ça match, on ajoute la confidence de l'observation au score du pilier. Plusieurs piliers peuvent matcher la même photo — une photo de café près d'une voiture peut être classée à la fois en "Cars" et en "Food".

// Pseudo-code de matching (vrai code dans VisionClassifier.mapToAllPillars)
for obs in observations where obs.confidence > 0.01 {
    let tokens = obs.identifier.lowercased().split(separator: "_")
    for pillar in pillars {
        let matched = pillar.terms.contains { term in
            tokens.contains { token in
                token == term || (term.count >= 4 && token.hasPrefix(term))
            }
        }
        if matched { scores[pillar.name] += obs.confidence }
    }
}

Étape 4 — Décision Vision vs cloud

On regarde le meilleur score Vision :

  • Si max ≥ 0.70 → on garde Vision, on renvoie tous les piliers au-dessus du seuil. Pas de cloud.
  • Si max < 0.70 et cloudAIEnabled == false → on garde les piliers Vision ≥ 0.55, on accepte une confiance basse.
  • Si max < 0.70 et max ≥ 0.30 et cloudAIEnabled == true → fallback Gemini Flash. Le seuil 0.30 évite de payer un appel API pour des photos qui n'ont aucun signal sur les piliers.

Étape 5 — Gemini (cas limites)

Quand on appelle Gemini, on lui envoie : l'image, et un prompt qui liste chaque pilier avec son about + ses reference tags. Il renvoie un tableau JSON [{pillarName, confidence, tags}, …].

Validation stricte côté Swift : on filtre les pillarName qui ne sont pas dans le Set des piliers connus — Gemini hallucine des catégories de temps en temps, on les jette.

Un seul retry après 500 ms si l'appel échoue. Au-delà, on retombe sur le résultat Vision même s'il est sous le seuil.

Étape 6 — Cadrage (passe séparée)

En parallèle de la classification thématique, on tag chaque photo d'un cadrage : portrait · wide · detail · pov · screenshot. Sert plus tard à choisir les bons slots dans les templates de post.

Détection screenshot par aspect-ratio + largeur exacte (iPhone modernes 2.1…2.25 et 1242 / 1284 / 1290 / 1320 px). Sinon, mêmes observations Vision mais matchées contre une autre table de termes pondérés par weight.

05. Réutilisation pour une autre app

Ce que tu peux copier-coller tel quel vs. ce qu'il faut adapter au nouveau domaine.

À reprendre tel quel

✓ Keep · 100%

PhotoBatchSequence

Streaming pull-based générique. Aucune dépendance domaine.

✓ Keep · 100%

Snapshot pattern

Convention SwiftData → struct. S'applique à n'importe quel @Model.

✓ Keep · 100%

GalleryClient (actor cache)

Lire/invalider. Renommer mais garder le pattern d'actor avec invalidations explicites.

✓ Keep · 100%

Vision request + deepCopyCGImage

Le deepCopyCGImage évite des crashes PhotoKit où le CGImage backing devient invalide pendant l'analyse async. Garder.

✓ Keep · 100%

Orchestration TaskGroup + cancellation

maxConcurrent, .cancellable(id:), propagation de CancellationError. Pattern indépendant du domaine.

✓ Keep · 100%

Cloud fallback seuil-gated

L'idée « on-device first, cloud derrière flag + signal minimum » se réapplique à toute feature ML hybride.

À adapter au nouveau domaine

⚠ Swap

VisionClassifier.fallbackKeywords

Table de mots-clés par catégorie. Hardcodée PostKit (cars/food/travel/business/fitness/bts). À redéfinir pour le nouveau domaine ou rendre data-driven via Remote Config.

⚠ Swap

PillarDefinition

Le DTO du domaine. Remplacer par TopicDefinition / CategoryDefinition selon l'app. Garder la structure : name · about · referenceTags.

⚠ Swap

CadrageDetector.cadrageTerms

Pondération portrait/wide/detail/pov est spécifique à PostKit (alimente les templates de post). Une app de tri photo classique n'en a pas besoin.

⚠ Swap

Prompt Gemini

Le prompt JSON inclut le mot "pillar" partout. Renommer en "topic" / "category" selon le domaine pour ne pas biaiser le modèle.

⚠ Swap

Seuils 0.70 / 0.55 / 0.30

Calibrés pour des piliers larges (catégories grand public). Une app avec catégories techniques pointues voudra des seuils plus élevés.

⚠ Swap

Screenshot detection (widths)

Liste de largeurs exactes iPhone à mettre à jour pour les nouveaux devices. À refresh chaque génération.

Checklist d'extraction

  • Copier Dependencies/ en entier, renommer Pillar* → YourTopic*.
  • Garder PhotoBatchSequence.swift sans modif.
  • Dans ImageClassifierClient.swift : remplacer la table fallbackKeywords, ajuster les seuils, ré-écrire le prompt Gemini, supprimer CadrageDetector si non pertinent.
  • Renommer GalleryClient → quelque chose qui colle au domaine (LibraryClient, CollectionClient).
  • Reprendre le scaffold d'orchestration depuis DashboardFeature.runFullScan (lignes 260-400 environ) — c'est le code-modèle.
