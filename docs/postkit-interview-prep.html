Overview

PostKit en 30 secondes

Un assistant de création de posts Instagram qui scanne la photothèque, classe les photos par thématiques (pillars), et génère des posts à partir de templates configurables.

Le pipeline

  • Onboarding → Quick Scan (20 photos, ~5s)
  • Full Scan → 20k+ photos, batches de 30
  • Core ML on-device → Gemini Flash fallback
  • Classification → Pillars → Templates → Posts

Les screens

  • Dashboard — pillars, scan status, scheduled posts
  • Explore — toutes les photos, filtres multi-critères
  • Classification — review des photos pending
  • Post Assembly — templates, slots, caption AI
  • SmartPost — prompt → template auto-généré

Architecture

Pourquoi TCA ?

Le choix

The Composable Architecture (Point-Free) plutôt que vanilla SwiftUI + @Observable.

Ce que TCA apporte ici

  • State déterministe — le scan de 20k photos manipule ~15 variables d'état simultanément (progress, counts, pillar updates). TCA garantit des mutations séquentielles et prédictibles.
  • Annulation structurée — .cancellable(id:) pour le scan, la génération de caption, le backfill cadrage. Chaque effet long est annulable proprement.
  • Testabilité — TestStore permet de vérifier chaque action/state transition du scan flow sans lancer l'app.
  • Dependency injection — @DependencyClient swap PhotoKit, SwiftData, Vision en un seul endroit.

Le trade-off assumé

  • Boilerplate — chaque feature = Reducer + State + Action + View. Plus verbeux que @Observable.
  • Courbe d'apprentissage — TCA a ses propres patterns (Effect, Presentation, delegate actions) qui ne sont pas standard SwiftUI.
  • Snapshot pattern — les @Model SwiftData ne sont ni Equatable ni Sendable, donc chaque entité a un struct Snapshot dédié pour vivre dans le TCA State.

Verdict

Pour un CRUD simple, TCA serait overkill. Ici, le scan orchestration avec 6 tâches parallèles, annulation, progress tracking temps réel, et 4 features présentées modalement justifie le framework.

ML Pipeline

Classification hybride — Core ML + Gemini

ÉTAPE 1

On-device, gratuit, ~50ms

→

DÉCISION

Confidence ≥ 0.70 ?

Oui → résultat final

→

ÉTAPE 2 (fallback)

Gemini 2.5 Flash

Cloud, ~200ms, ≥ 0.30 requis

Comment ça marche

  • Vision retourne des labels génériques ("car", "beach", "food")
  • On mappe ces labels aux pillars via keyword matching : reference tags de l'utilisateur + description du pillar + fallback keywords hardcodés
  • Les scores sont accumulés par pillar — une photo peut matcher plusieurs pillars
  • Gemini reçoit un prompt structuré avec les descriptions des pillars et retourne du JSON

Limites connues

  • Seuils empiriques — 0.55/0.70/0.30 ajustés manuellement, pas de dataset de validation formel
  • Keyword matching fragile — dépend de la qualité des labels Vision et des termes choisis par l'utilisateur
  • Pas de modèle custom — un CreateML fine-tuné sur les pillars de l'utilisateur serait plus précis (Phase 2)
  • Gemini coût — ~$0.01/1000 photos estimé, pas de tracking en prod

SwiftData — Le pattern Snapshot

// SwiftData model — lié au ModelContext
@Model class Pillar {
    var name: String
    var emoji: String
    var about: String
    ...
}

// Snapshot — Equatable, Sendable, Identifiable
struct PillarSnapshot: Equatable, Sendable, Identifiable {
    let id: UUID
    var name: String
    var emoji: String
    ...
}

// Conversion
extension PillarSnapshot {
    init(_ model: Pillar) { ... }
}

Pourquoi ce pattern ?

  • @Model n'est ni Equatable ni Sendable
  • TCA State exige Equatable pour le diffing
  • Les Effects async exigent Sendable pour traverser les frontières d'isolation
  • Un @Model est lié à son ModelContext — on ne peut pas le passer entre threads

Interview Q&A

Questions anticipées — Partie 1

"Pourquoi TCA et pas @Observable ?"

Le scan orchestre 6 tâches parallèles avec annulation, progress tracking, et 15 variables d'état mutées simultanément. Avec @Observable j'aurais dû gérer moi-même les cancellation tokens, le threading des mutations d'état, et le testing des effects async. TCA me donne ça out of the box. Pour les écrans simples (Settings, PhotoDetail), TCA est effectivement plus verbeux qu'il ne faudrait — c'est le trade-off.

"Comment tu gères les erreurs côté utilisateur ?"

Le scan est conçu pour être résilient : chaque photo qui échoue est skippée individuellement (le catch est par photo, pas par batch). Le scan est idempotent — si l'app crash, il reprend là où il en était grâce au Set<String> des asset IDs déjà classifiés. Côté UI, c'est un point faible actuel : l'utilisateur ne voit pas combien de photos ont échoué silencieusement. C'est dans la roadmap d'ajouter un "scan report" post-scan avec les métriques (classifiées, pending, erreurs).

"Les seuils de classification, ils viennent d'où ?"

Tuning empirique sur ma propre bibliothèque (~20k photos). 0.55 est le minimum pour éviter les faux positifs, 0.70 est le seuil de confiance élevée qui évite l'appel Gemini. 0.30 est le plancher Vision pour déclencher Gemini — en dessous, la photo n'a aucun signal pertinent. Pour une v2, je mettrais en place un dataset de validation avec des photos labelisées manuellement pour mesurer precision/recall.

Interview Q&A

Questions anticipées — Partie 2

"Ça scale comment à 100k photos ?"

Le scan lui-même scale bien grâce au streaming par batches de 30 avec backpressure (buffer de 3 batches max en mémoire). Le point de contention est le dashboard onAppear qui charge tous les ClassifiedPhotoSnapshots en mémoire pour enrichir les pillars. À 100k, il faudrait passer à une requête agrégée SwiftData (GROUP BY pillarID) au lieu du fetch-all + filter in-memory. Explore aurait aussi besoin de pagination (fetchLimit + fetchOffset) — actuellement tout est chargé d'un coup.

"Le scan est idempotent ?"

Oui. Au démarrage du scan, on charge le Set de tous les asset IDs déjà classifiés. Chaque photo déjà traitée est skippée. batchSavePhotos fait un upsert (fetch by assetLocalIdentifier + update or insert). Si l'app crash à mi-scan : fullScanComplete n'est jamais set, donc le scan reprend automatiquement au prochain lancement. Les photos déjà sauvées ne sont pas re-traitées.

"Sécurité de la clé Gemini ?"

La clé est dans Secrets.xcconfig (non commité) et injectée via Info.plist. Elle finit en clair dans le binaire — c'est une limite connue. Pour la prod, la bonne approche est un proxy server-side (Cloud Function) qui valide le receipt StoreKit avant de proxier l'appel Gemini. Ça élimine la clé du device et permet du rate-limiting par utilisateur. Planifié pour Phase 2 avec la monétisation.

Optimisations réalisées

  • TaskGroup avec throttle (6 concurrent) au lieu de séquentiel
  • async let pour classify ∥ detectCadrage
  • AsyncStream avec backpressure (.bufferingNewest(3))
  • SwiftData: bulk ops sur background ModelContext
  • Dashboard onAppear: 6 queries parallèles (async let)
  • autoreleasepool pour drainer les objets Vision
  • OSAllocatedUnfairLock contre les double-resume
  • Cancellation propagation à tous les niveaux

Améliorations prévues

  • Pagination Explore (fetchLimit/fetchOffset)
  • Requête agrégée SwiftData pour le dashboard (GROUP BY)
  • PHCachingImageManager pour pré-chauffer les thumbnails
  • Scan report UI (succès/erreurs/skips)
  • Dataset de validation pour les seuils ML
  • Proxy server-side pour Gemini

Retrospective

Ce que je ferais différemment

Bon appels

  • TCA pour le scan engine — la complexité d'état justifie le framework
  • Snapshot pattern — propre separation SwiftData ↔ TCA
  • Hybrid classifier — on-device first, cloud fallback = bon UX + contrôle des coûts
  • Design system dès le début — tokens cohérents, pas de magic numbers UI
  • Batch processing — stream + batch save + progress tracking

Si c'était à refaire

  • Tests dès le début — le TestStore de TCA est un superpouvoir que j'ai sous-utilisé
  • Pagination Explore dès le MVP — charger toutes les photos d'un coup ne scale pas
  • Agrégation SwiftData — le dashboard devrait utiliser des queries optimisées, pas du fetch-all + filter
  • CreateML custom — le keyword matching sur VNClassifyImageRequest est un hack intelligent mais fragile
  • Server-side Gemini dès le jour 1 — la clé dans le bundle est une dette technique
