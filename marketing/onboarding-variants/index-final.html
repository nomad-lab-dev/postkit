Implementation spec — SwiftUI + TCA

Below is the technical specification for shipping this onboarding in PostKit. The structure maps onto a TCA OnboardingFeature reducer with one state branch per step. Every step is independently testable. Photos throughout are pulled from PhotoLibraryClient (real) or MarketingPhotoLibraryClient (demo-mode).

STATE Global onboarding state

// OnboardingFeature.State
@ObservableState struct State: Equatable {
  var step: Step = .hook
  var pillars: [PillarDraft] = .default3  // editable
  var scanProgress: ScanProgress = .init()
  var demoPrompt: DemoPrompt = .italy   // step 02 active chip
  var selectedFirstPrompt: PrefilledPrompt? = nil
  var hookMode: HookMode = .without    // step 01 toggle
  var firstPostDraft: GeneratedPostSnapshot? = nil
}
enum Step { case hook, demo, pillars, scan, firstPrompt }

01 Hook — Before/After toggle

UX

  • Segmented control top: Without / With PostKit.
  • Without: chaotic photo cloud — 9 random thumbnails from the user's gallery, scattered with rotations (−9°..+9°).
  • With PostKit: mini-bento 2×2 with mock pillar names (Travel, Coffee, Cars, Build) + 1 preview thumbnail per cell. The photos used are the same gallery thumbnails as the Without state — just organised. Drives the "same photos, different relationship" mental model.
  • Transition: 0.45s opacity + scale cross-fade between panes. SwiftUI: matchedGeometryEffect between modes lets specific thumbnails fly to their bento cells.

Action wiring

case hookToggle(HookMode)               // updates state.hookMode
case hookContinueTapped                  // → state.step = .demo

Data needed

  • photoLibrary.fetchRecentPhotos(limit: 9) — pulled at .onAppear
  • If permission denied → fallback to MarketingPhotoLibraryClient bundled samples

02 Demo — Smart Post showcase

UX

  • 3 prompt chips at the bottom: 🌍 Italy / ☕ Coffee / 💼 Build. Tapping a chip swaps the demo card content.
  • Demo card = chat bubble + 2×2 photo grid + generated caption + "Generated · 2.1s" timestamp.
  • Photos for each demo come from the MarketingPhotoLibraryClient bundle — not the user's gallery (since permission hasn't been requested yet at this step).
  • Transition between chip selections: 0.3s opacity fade on the demo card content.

Action wiring

case demoChipTapped(DemoPrompt)            // state.demoPrompt = ...
case demoContinueTapped                    // → state.step = .pillars
💡 No permission requested yet. This is intentional — the user sees the magic before being asked to grant photo access, which raises consent rates dramatically (foot-in-door psychology).

03 Pillars — editable list

UX

  • 3 default pillars pre-shown: 🌍 Travel · ☕ Food & coffee · 💼 Build in public.
  • Each pillar row has: tappable name (inline rename), × button (remove).
  • "+ Add another" row with text input + emoji selector + primary plus button.
  • Continue CTA label updates dynamically: "Continue with N pillars →".
  • Constraints: minimum 2 pillars, maximum 7. CTA disabled outside this range.
  • Animations: new pillar slides in from top (0.3s ease). Removed pillar fades out + collapses (0.25s).

Action wiring

case pillarRenamed(id: UUID, name: String)
case pillarRemoved(id: UUID)
case pillarAdded(name: String, emoji: String)
case pillarsContinueTapped                   // → state.step = .scan
                                            //   + photoLibrary.requestAuthorization()

Permission request placement

Photo authorisation is requested on the Continue tap of step 03 — right before the scan begins. The system prompt fires inside the .run effect; if denied, the coordinator routes to a recoverable explainer screen ("PostKit needs photo access to sort your library, but you can grant limited access in Settings"). It is NOT requested at app launch.

04 Scan — bounded incremental classification ★

UX

  • Live progress bar per pillar (0/20 → 20/20).
  • Total counter at the bottom (X / 500 photos scanned).
  • Animated status text cycles through: "Reading photo N…", "Found 12 Travel moments", "Tagging in Cars…", "Reading photo N…", etc. Cycles every 1.2 sec.
  • CTA disabled until exit conditions are met. Disabled state text: "Building your library…". Once met, button transforms with pulse animation to "Continue · your gallery is ready →".
  • Once met, screen does NOT auto-advance — user taps CTA to acknowledge. (Auto-advance is jarring on success states.)

Exit conditions (OR-gated)

ConditionWhy
≥ 20 photos in every pillarEnough samples to draft 6-photo posts comfortably for each pillar
OR 500 photos total scannedHard ceiling so users with small galleries still complete onboarding (5K-photo cap doesn't gate them)
OR 100% of library scannedFor users with <500 photos, exit when nothing left to scan

Scan strategy

  • Pull batches of 30 photos from PhotoLibraryClient.fetchAllPhotos(batchSize: 30).
  • For each photo, run imageClassifier.classify (Core ML on-device).
  • Confidence < 0.55 → mark .pending, doesn't count toward pillar bucket.
  • Confidence ≥ 0.55 → write to SwiftData via persistence.batchSavePhotos + increment in-state counter for that pillar.
  • After each save, re-evaluate exit conditions. When met → cancel the scan effect.

Action wiring

case scanStartRequested                  // fires on .onAppear of scan step
case scanPhotoProcessed(pillarID: UUID?, confidence: Float)
case scanExitConditionsMet               // CTA becomes pulse-ready
case scanContinueTapped                  // → state.step = .firstPrompt
                                          //   + background continues scan
💡 The scan continues in background after onboarding ends. The 20-per-pillar / 500-total exit conditions are just for unblocking onboarding. A separate background task (Dashboard's startFullScanRequested already implements this) processes the rest of the gallery overnight or on next app open.

05 First prompt — guided commit

UX

  • Typewriter-style typed prompt input: "A post about my Italy trip".
  • 3 prefill chips below input, generated from the user's confirmed pillars. Tapping a chip swaps the typed text + the post preview's photo + caption.
  • Live IG-style post mockup updates as user changes prompt.
  • "Save · I'm in →" CTA fires the actual SmartPostFeature.sendMessageTapped with the prefilled prompt, then opens the PostEditorFeature sheet with the filled slots.

Action wiring

case firstPromptChipTapped(PrefilledPrompt)
case firstPromptSaveTapped               // → triggers SmartPost flow
                                          //   + sets onboardingComplete = true
                                          //   + dismisses sheet, lands user on Dashboard

FX Transitions between steps

  • Step 01 → 02 : horizontal slide (matchedGeometryEffect carries one bento thumbnail into the demo card photo 1).
  • Step 02 → 03 : standard slide. Prompt chip pillar names carry into the editable pillar list (smart UX shortcut).
  • Step 03 → 04 : the 3-4 pillar rows fade up, the scan stack fades down → photos appear to "leave" the cards and start being sorted.
  • Step 04 → 05 : 20 → 20 counters morph into the "20 photos · ready" line in the post preview.
  • Step 05 → Dashboard : matchedGeometryEffect on the IG post mockup → it becomes the top card in the Dashboard's "Today" section.

META Accessibility & edge cases

  • Reduce Motion ON: all transitions become 0.2s opacity-only. No translation/scale.
  • Dynamic Type: Instrument Serif titles use the .title2 scaling family with clamps at .accessibility3.
  • Reduce Transparency: glass surfaces fall back to opaque Palette.surface.
  • Photo permission denied: after step 03, route to recovery screen with deep-link to iOS Settings. Sample bundled photos used for demo card on step 02 in this case.
  • Small library (< 100 photos): skip step 04 entirely. Scan completes in <5sec. Land directly on step 05 with all detected pillars.
  • Empty pillars after scan: if a pillar has 0 high-confidence matches, show in step 04 results as "We didn't find enough X yet — we'll keep looking." Don't surface in step 05 prefills.

DONE Definition of done

  • All 5 steps reachable from OnboardingFeature.State() initial state.
  • State persists across kill-restart (uses UserDefaults("onboarding.step") as save point).
  • Onboarding complete writes UserDefaults("onboardingComplete") = true + clears the step pointer.
  • Resumability: if user kills app at any step, next launch returns to that step (with scan progress restored from SwiftData counts).
  • Test coverage: each step has its own TestStore assertion suite. Scan logic has a fake clock-driven test verifying exit conditions.
